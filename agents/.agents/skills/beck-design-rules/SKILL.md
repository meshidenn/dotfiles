# Beck の設計ルール

現在のタスクの設計を、次の4原則で評価する。

設計の本来の基準は、ソフトウェアの生涯にわたる費用と便益である。しかし、それは事後にしか測れない。4原則は、今あるコードに対して今すぐ評価できる基準である。

## 4原則

優先順位の高い順に示す。

1. **テストが通る：** 意図したとおりに動くことを最優先にする。テストは、それを確かめる手段である。
2. **意図が伝わる：** 書き手の目的を、読み手がコードから理解できるようにする。構造と命名で表す。
3. **重複がない：** 同じ知識やロジックを1か所だけに書く。並行するクラス階層のような、隠れた重複も探す。重複を取り除く作業は、良い設計を引き出す手段になる。
4. **要素が最小限である：** 上の3原則に貢献しないクラスやメソッドなどの要素を取り除く。将来の要件に備えて足した柔軟性のための要素は、多くの場合、変更をかえって難しくする。

## 原則どうしの関係

- 原則が対立する場合は、上位の原則を優先する。要素を減らすために、振る舞いや分かりやすさを犠牲にしない。
- 原則2と3の順序は重要ではない。意図の明確化と重複の排除は、互いを改善する。
- 分かりやすくするために重複を残したくなった場合は、先に、別の問題が隠れていないかを調べる。重複を残すことは、多くの場合、その問題を覆い隠すだけである。
- 原則2と3が実際に対立することは稀である。主な例はテストコードである。その場合は、読み手にとっての分かりやすさを優先する。

## 評価の手順

1. 関係するテストを実行し、結果を確認する。テストがない振る舞いと、実行できなかったテストを記録する。テストの成功だけで、正しさが証明されたとはみなさない。
2. 原則2〜4について、対象のコードから根拠になる箇所を探す。原則を機械的な採点には使わない。
3. 指摘ごとに、改善案とそのトレードオフを考える。上位の原則を損なう改善案は採用しない。振る舞いを変える改善案と、名前についての改善案は、「関連スキル」の指定に従う。
4. 結果を、次の出力形式で示す。

## 出力形式

指摘ごとに、次の項目を示す。指摘がない原則は、「指摘なし」と書く。

- **原則：** 4原則のどれに関する指摘か。
- **根拠：** ファイルと行、該当するコード。
- **指摘：** その箇所が原則を満たしていない理由。
- **改善案：** 変更の内容と、関係するトレードオフ。
- **未確認の範囲：** テストで確かめていない振る舞い、読んでいないコード。

## 適用の範囲

- 4原則は評価の基準であり、変更の許可ではない。リファクタリングは、ユーザーの指示とプロジェクトの承認ルールの範囲内で行う。範囲外の改善は、提案として示す。
- 承認された変更を行った場合は、テストを再実行し、振る舞いが保たれたことを確かめる。

## 関連スキル

次の場面では、該当するスキルを必ず使う。

- **振る舞いを変更する場合：** `canon-tdd` の手順で進める。原則1の指摘を直す場合と、改善案が振る舞いの変更を含む場合が該当する。TDD の途中で見つけた重複の扱い（重複は手掛かりであり、すぐに抽象化する義務ではない）も、`canon-tdd` に従う。
- **意図を明らかにする場合：** 名前についての判断は、進化的命名（`naming-as-a-process`）で行う。現在の段階を判定し、改善案には名前の変遷を示す。
