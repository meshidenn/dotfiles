# 命名を段階的に改善する

一度で完璧な名前を考えない。コードを1か所見て、気づきを1つ得て、それを名前に記録する。これを繰り返して段階を1つずつ進め、依頼の目的に十分な名前になったら止める。すべての対象を最後の段階まで進める必要はない。

名前は、読み手が本体を読まずに済ませるための手段である。したがって、名前が実装と食い違うことを最も重い問題として扱う。

## 1. 現在の段階を判定する

| 段階 | 判定の基準 |
| --- | --- |
| 1. 名前がない・誤解を招く（Missing or Misleading） | 1つの概念を成す処理やデータのまとまりに名前がない。または、名前が実装と食い違う、重要な振る舞いを伏せている、何も伝えないのに仮名とも分からない、のいずれかである。 |
| 2. 明らかな仮名（Obvious Nonsense） | 名前は何も伝えないが、仮名であることは誰にでも分かる。 |
| 3. 正直な名前（Honest） | 確かめた事実を1つ表し、未確認の部分があることも示している。 |
| 4. 完全に正直な名前（Completely Honest） | 対象が行うことをすべて表している。名前だけを渡された人が、本体の処理を過不足なく挙げられる。 |
| 5. 適切な責務（Does the Right Thing） | 完全に正直な名前のまま、無関係な責務や、呼び出し側から隠したい関心事を含まない。 |
| 6. 意図が伝わる名前（Intent Revealing） | 何をするかではなく、呼び出し側がなぜそれを使うかを表している。 |
| 7. ドメインの抽象化（Domain Abstraction） | 周囲の名前と合わせて、共有されたドメイン概念を表している。 |

段階1〜4は理解を名前に記録する過程、段階5は責務を整理する過程、段階6〜7は文脈と設計を明確にする過程である。

## 2. 次の段階へ進める

各遷移では、決まった場所を見て、気づきを1つだけ探す。見る場所は段階ごとに違う。兆候の一覧は `references/stage-guide.md` にある。

### 1 → 2：範囲を決めて、仮名にする

- **見る場所：** 作業に関係する長いメソッド・クラス・引数リスト・式。読んでいる途中で出会った名前。
- **探すもの：** まとまりを成す塊を1つ。または、実装と食い違う名前を1つ。
- **書き留め方：** 対象の範囲を決め、`applesauce` のような仮名を付ける。この時点では良い名前を考えない。
- **完了の基準：** 範囲を決める判断と、名付ける判断が分かれている。

すでに内容が分かっている対象は、仮名を経ずに 2 → 3 から始めてよい。

### 2 → 3：事実を1つ書く

- **見る場所：** 対象の本体。
- **探すもの：** 中心になっている処理を1つ。外部要素（DB、画面、ネットワーク）、戻り値の出どころ、何度も使われる値が手掛かりになる。
- **書き留め方：** 確かめた事実を具体的に書く。確信がなければ `probably_` を前に付け、ほかにも処理があれば `_and_stuff` を後ろに付ける。
- **完了の基準：** 名前に嘘がなく、未確認の部分があることが読み取れる。

### 3 → 4：節を1つずつ足す

- **見る場所：** 対象の本体。まだ追っていないデータや引数。
- **探すもの：** 名前にまだない処理を1つ（既知を広げる）。または、対象が行わないことや部分的な事実を1つ（未知を狭める）。
- **書き留め方：** 節を1つ足す。既存の節を広い語に置き換えて吸収しない。長い名前と接続詞を許容する。
- **完了の基準：** 関係するデータをすべて追跡したら `_and_stuff` を外す。既知の部分をテストで裏付けたら `probably_` を外す。

### 4 → 5：名前を見て、責務を分ける

- **見る場所：** 名前だけ。本体と呼び出し元は見ない。
- **探すもの：** ほかの節と無関係な節。または、呼び出し側から隠したい関心事を表す節。
- **書き留め方：** 構造を変えて、責務を分離するか隠蔽する。そのあとで、名前を実態に合わせる。
- **完了の基準：** 名前が完全に正直なまま、納得できる内容になっている。

### 5 → 6：呼び出し元を見て、目的を書く

- **見る場所：** すべての呼び出し元と、その前後の処理。
- **探すもの：** 対象が、より大きな流れの中で果たす目的。
- **書き留め方：** 目的を表す名前に改める。完全に正直な名前のうち、使う場面の判断に役立つ部分は残す。
- **完了の基準：** 別の呼び出し元で読んでも意味が通る。通らない場合は、意図が違うか、責務の分け方が合っていない。

### 6 → 7：名前の集まりを見て、概念を作る

- **見る場所：** 関連するメソッドやクラスの集まり。
- **探すもの：** 基本型のまま扱われているドメイン概念（Primitive Obsession）。
- **書き留め方：** その概念を表す型（Whole Value）を作り、その値を扱っていた処理を移す。
- **完了の基準：** 次に足す処理の置き場所が自明になっている。

## 3. 守る規則

- **誤解を招く名前を先に直す。** 誤った内容を伝える名前は、何も伝えない名前より害が大きい。
- **具体的に書く。** 段階3〜4では、すべてを包む語（`process`、`handle`、`manage` など）を使わない。一般的な名前は、名前に入っていない処理を見えなくする。
- **推測を確定事項として書かない。** 本体で確かめていない内容は、未確認として区別する。
- **名前を変えたければ、先に振る舞いを変える。** 都合の悪い節を名前から消すだけの変更をしない。長い名前を短くする手段は、責務の分離（段階5）と、目的の名前（段階6）である。
- **意図の段階では理由を書く。** 呼ばれる時点、開始時の状態、ソフトウェア工学の用語、ほかで使わない一回限りの概念で名付けない。
- **意図が違えば入口を分ける。** 実装が同じでも、呼び出す目的が違う場合は、実装を共有する別の名前を提案する。重複を統合する前に、実装だけでなく意図も一致するかを確かめる。

## 4. クラスと変数

- **クラス：** 段階3〜4では、持っている責務をすべて挙げる。責務が多すぎるかどうかは段階5で判断する。段階6では、呼び出し側がそのクラスに任せたいことを表す。
- **変数：** 段階3〜4では、使われ方をすべて挙げる。段階6では、同じ型のほかのインスタンスとの違いと、その文脈での用途を表す。型と同じ名前は情報を持たない。

## 5. 途中段階の名前の扱い

段階2〜4の名前（仮名、`probably_`、`_and_stuff`、長い列挙）は、事実を先に確かめるための作業用の名前である。

- 途中の名前は、応答の中に「名前の変遷」として示す。コードには、到達した段階の名前だけを書く。
- 段階を飛ばさない。変遷を示せない名前は、確かめた事実ではなく推測に基づいている。
- 未確認の部分が残ったまま止まる場合は、その範囲を報告する。`probably_` や `_and_stuff` を付けた名前をコードに入れるかどうかは、ユーザーに確認する。

## 6. 出力形式

命名レビューや命名案では、対象ごとに次の項目を示す。

- **対象：** ファイルと行、現在の名前。
- **現在の段階：** 判定と、その根拠になる実装または使用箇所。
- **名前の変遷：** 段階ごとの名前と、その段階で確かめた事実。
- **提案する名前：** 到達した段階と、そこで止める理由。
- **必要な構造変更：** 段階5以降に進むための抽出・移動・型の追加。ない場合は省く。
- **未確認の範囲：** 追跡していないデータ、呼び出し元、動的な参照。

## 7. 適用と検証

- 改名、抽出、責務の移動は、ユーザーの依頼とプロジェクトの承認ルールの範囲内で行う。範囲外の変更は、提案として示す。
- 改名では、参照先をすべて追跡する。公開 API、設定や永続化で使う名前、文字列による参照への影響を確認する。可能な場合は、手作業の置換ではなく、言語サーバーなどの改名機能を使う。
- 名前の表記は、言語とプロジェクトの命名規約に合わせる。このスキルの例は Python の表記である。
- コミットする場合は、改名と構造変更を別のコミットに分ける。
- 実装を変更した場合は、関係するテストと必要なビルド・型検査を実行し、振る舞いが保たれたことを確かめる。未検証の範囲は伝える。
