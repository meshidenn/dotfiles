# 段階ごとの手掛かり

`SKILL.md` の各遷移について、「どこを見るか」「何を探すか」を具体化した一覧。兆候は機械的な判定基準ではなく、調べる場所の候補として使う。各節の末尾に、対応する出典の記事番号を示す。コード例はこのスキルのために作ったもので、出典の例ではない。

## 段階1：名前がない箇所を見つける

長いものを見る。長いメソッド、クラス、ファイル、引数リスト、式は、複数の概念を含むことが多い。その中から、まとまりを成す塊を1つ選ぶ。

- 空行で区切られた文のまとまり
- 一読で意味が取れない式（算術や論理演算を含むもの）
- いつも一緒に渡される引数の組
- メソッド内で組として使われる引数（例：値と、その値が有効かを示すフラグ）

最良の塊を探す必要はない。どの塊を選んでも、理解は1歩進む。

長いメソッドで塊を選ぶときは、次の方法が使える。

- **末尾から探す。** 長いメソッドは、ガード節、入力の取り出し、処理、結果の計算、書き込みまたは返却の順に並ぶことが多い。重要な処理は末尾に近い。
- **二分探索で読む量を減らす。** 目的に関係しない大きな塊か、関係する小さな塊を探す。関係しない塊は、正直な名前（段階3）まで進めて、先へ進む。
- **制御構造に沿って切る。** 1つのループや分岐がメソッドの大半を占める場合は、その本体が候補になる。制御構造が並ぶ場合は、それぞれを丸ごと切り出す。`try` の本体も候補になる。複雑な `except` 節は、通常は切り出さない。

（Article 2）

## 段階1：誤解を招く名前を見つける

読んでいる途中で出会った名前について、情報の不足と誤りを探す。

- 呼ばれる時点で名付けたメソッド（`on_load`、`pre_init`）。何が起きるかを伝えない。
- 型と同じ名前の変数（`invoice: Invoice`）。どのインスタンスかを伝えない。
- 重要な振る舞いを伏せた名前（`build_display_name` が DB への書き込みも行う）。
- `-er`、`-Manager`、`-Utils`、`-Operations` で終わる名前（`ReportManager`、`calc_utils`）。責務を伝えない。

（Article 2・3）

## 段階3：事実を1つ見つける

本体を読み、中心になっているものを1つ選ぶ。

- 外部要素を表す変数（DB、画面、ネットワーク、外部サービス）
- 戻り値の出どころ
- 何度も使われる値や、ほかのメソッドと共通するパターン

扱いやすさや危険度についての評価も、気づきとして名前に書いてよい。

一般的すぎる名前は、嘘ではなくても役に立たない。次の2つのうち、DB の行を上書きするという危険を読み手に伝えるのは後者だけである。

| 名前 | 評価 |
| --- | --- |
| `handle_shipment_somehow` | 正直だが、何に触るかが分からない。 |
| `probably_overwrite_shipment_rows_in_db_and_stuff` | DB の行を上書きすることと、未確認の処理が残ることが分かる。 |

具体的な名前にしておくと、段階4では節を足すだけで済む。一般的な名前は、残りの処理もおおよそ含んでいるように見えるので、名前に入っていない処理を見つけにくくする。

（Article 3）

## 段階4：名前を完全にする

名前は3つの部分から成る。

| 部分 | 役割 | 外す条件 |
| --- | --- | --- |
| `probably_` | 中央の部分にも確信がないことを示す。 | 中央の部分をテストで裏付け、未知の範囲が末尾の部分に収まっていると確かめた。 |
| 中央 | 確かめた処理を列挙する。 | 外さない。 |
| `_and_stuff` | 未確認の処理があることを示す。 | 関係するデータをすべて追跡し、ほかに影響がないと確かめた。 |

1回の反復では、次のどちらかを1つだけ行う。

- **既知を広げる。** 本体から処理を1つ見つける（作用、計算、結果、状態の変更）。すでに名前にある処理の一部でなければ、中央に節を足す。
- **未知を狭める。** まだ追っていないデータを1つ選び、対象の中での使われ方を追う。行わないことや部分的な事実が分かれば、末尾の部分を具体化する（`_and_do_something_to_cache_and_stuff` → `_and_read_something_from_cache_and_stuff`）。

長いメソッドでは、理解のために塊を一時的に抽出してよい。ガード節はその典型である。ガード節は通常は名前に入れないが、残りの処理を読みにくくする。抽出した塊は、主対象の名前に必要かどうかが分かる段階まで進めれば足りる。

名付け方は、その後の変更の方向に影響する。

- **何であるかで名付ける。** 関連する機能がそこに集まる。凝集させたいときに使う。
- **何をするかで名付ける。** 名前を短くしたいという動機が、処理を減らす方向に働く。分割したいときに使う。

（Article 4）

## 段階5：分離する責務を見つける

名前の節を1つずつ見て、次の2つを問う。

1. この節は、ほかの節と無関係か。
2. この節は、呼び出し側から隠したい関心事か。

該当する節があれば、名前ではなく構造を変える。

- **責務を分ける。** メソッドを分割し、呼び出し元がそれぞれを個別に呼ぶ形にする。分割した部分の間を流れるデータは、1つの値にまとめて受け渡す。
- **隠蔽する。** 引数として受け渡している値を、それを所有するクラスのフィールドへ移す。呼び出し元とその上位から、その値への参照を取り除く。

多くの責務を抱えたクラスは、周囲のコードの問題（ユーティリティクラス、基本型への執着、特例の分岐）と互いに支え合っている。一度に分割せず、責務を1つずつ移す。

（Article 5）

## 段階6：目的を見つける

周囲の名前が段階3〜4に達していないと、流れの中での目的は見えにくい。必要なら、先に周囲の名前を進める。

目的として使えるものの例を示す。

| 対象 | 目的の候補 |
| --- | --- |
| メソッド | 達成する事後条件。行う変換。置き換える業務手続き。引き受ける中心的な責務。呼び出し側が気にしなくて済むようになること。 |
| クラス | メソッドに共通する責務。現実世界での実体。呼び出し側が任せたい責務。 |
| 変数 | 同じ型のほかのインスタンスとの違い。その文脈での用途。 |

この段階は、情報を意図的に減らす。「何をするか」の一部を「なぜ使うか」に置き換えるので、読み手は名前を信頼するしかない。完全に正直な名前のうち、使う場面の判断に役立つ部分は残す。

次の名前は、付けた直後は意味が通るが、文脈を忘れると意味を失う。

- 使う理由ではなく、使う時点で付けた名前（`post_upload_step`）
- 開始時の状態で付けた名前（`handle_unvalidated_order`）
- ほかのどこにも現れない、一回限りの概念
- ソフトウェア工学の用語（`OrderProcessor`、`execute`、`DataHandler`）

（Article 6）

## 段階7：欠けているドメイン概念を見つける

高水準のドメインの操作を、低水準の型だけで表している箇所を探す。次の兆候は、概念が1つ欠けていて、周囲のコードがその代わりをしていることを示す。

**クラスの集まり**

- 互いに強く依存し、外部との接点が少ない。
- あるクラスのメソッドが、別のクラスの公開された値を何度も読む。
- 名前が似ている（`Coupon` と `CouponValidity`、共通の接頭辞や接尾辞）。
- 寄せ集めを示す名前（`-Manager`、`-Transform`）や、結果ではなく動作を示す `-er` で終わる名前がある。

**メソッドの集まり**

- 同じ引数の組を取る。
- 同じフィールドの組だけを使う。
- 名前が対になっている（開始と終了、作成・読み取り・更新・削除）か、類義語を含む。
- 数行にわたって同じ変数を操作し続ける塊がある。
- よく一緒に呼ばれる。
- 名前に同じ語句が繰り返し現れるが、対応する名詞がシステムにない。

**フィールドと引数**

- 型が表せない内容を、名前で絞っている（`postal_code: str`）。
- 許容される値や解釈を、名前で示している（`timeout_ms: int`、`mode_flags: int`）。

概念を見つけたら、型を作り、その値を扱っていた小さな処理を集める。集めた処理は、実装と意図の両方を比べる。

| 実装 | 意図 | 扱い |
| --- | --- | --- |
| 同じ | 同じ | 伝わりやすいほうの名前に揃えて、1つにする。 |
| 同じ | 違う | 別の名前のまま残す。 |
| 違う | 同じ | 不具合か、意図の細かな差である。共通の接頭辞と、差を示す語で名付ける。共通点と差を確かめるテストを対で書く。 |

（Article 7）
