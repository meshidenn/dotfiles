# Canon TDD

依頼された振る舞いの変更を、小さなサイクルで進める。目指す状態は次の4つである。

- これまで動いていたものが、引き続き動く。
- 新しい振る舞いが、期待どおりに動く。
- システムが、次の変更に進める状態にある。
- 上の3点について、書き手と関係者が確信を持てる。

この手順を、あらゆる開発で必須とはみなさない。

## 工程ごとに集中すること

設計には、振る舞いの呼び出し方（インターフェース）と、振る舞いの実現方法（実装）の2種類がある。この2つを同じ工程で扱わない。

| 工程 | 集中すること |
| --- | --- |
| 1. シナリオを列挙する | 振る舞いの分析 |
| 2. 1件だけテストにする | インターフェースの設計 |
| 3. 失敗から成功へ進める | テストを通すこと |
| 4. 必要なら設計を改善する | 実装の設計 |

## 進め方

1. **シナリオを列挙する：** 新しい振る舞いのバリエーションと、維持すべき既存の振る舞いを一覧にする。実装の設計は、この工程で決めない。一覧は応答に示し、実装前の Plan としてユーザーの承認を得る。
2. **1件だけテストにする：** 一覧から1件を選び、準備・呼び出し・アサーションを備えた実行可能なテストを書く。選んだ理由を一言添える。テストの順序は、作業の進めやすさと最終的なコードの両方に影響する。全件を先にテストコードへ変換しない。
3. **失敗から成功へ進める：** テストが失敗することを確認し、そのテストと既存のテストが通るよう実装を変更する。リファクタリングを混ぜない。通った項目は、一覧で完了にする。
   - 新しいシナリオに気づいたら、一覧に追加する。
   - 追加したシナリオがこれまでの実装を無効にする場合は、続行するか、テストの順序を変えてやり直すかを選ぶ。出典は後者を勧める。やり直しは書いたコードの破棄を伴うので、実行前にユーザーに確認する。
   - テストが最初から通った場合は、実装かアサーションを一時的に変えて、テストが失敗することを確かめる。変更を元に戻してから、その項目を完了にする。
4. **必要なら設計を改善する：** 実装の設計は、テストが通ったあとのこの工程で決める。この工程は任意である。今回の作業に必要な範囲を超えて整理しない。重複は手掛かりであり、すぐに抽象化する義務ではない。リファクタリングの承認がない場合は、コードを変更せずに候補を記録する。
5. **一覧が空になるまで繰り返す：** 工程2に戻り、次の1件を選ぶ。一覧の追加と完了は、応答の中で更新して示す。

## 工程ごとの名前の扱い

全工程で、進化的命名（`naming-as-a-process`）を使う。名前は、その時点で分かっている設計を記録したものとして扱う。名前と実装の食い違いや、名前の付けにくさは、設計についての情報である。

| 工程 | 名前の扱い | 名前から読み取る設計情報 |
| --- | --- | --- |
| 1 | シナリオを、振る舞いを表すドメインの語で書く。実装の名前は決めない。 | 同じ概念に別の語を使っていないか。語が足りない概念はないか。 |
| 2 | テスト名はシナリオを表す。呼び出す関数や引数は、呼び出し側の目的で名付ける（意図が伝わる名前）。 | テストが最初の呼び出し元になる。目的を一言で名付けられない場合は、インターフェースが複数の責務を持っている可能性がある。 |
| 3 | 新しく作った内部の要素には、正直な名前を付ける。良い名前を考えない。既存の名前は変えない。 | 実装が工程2の名前と食い違った場合は、その食い違いを記録する。 |
| 4 | 名前を完全に正直にする。次に、名前だけを見て責務を分け、意図が伝わる名前へ進める。 | 無関係な節は、責務の分離の候補である。基本型の繰り返しは、欠けているドメイン概念の候補である。 |
| 5 | 完全に正直な名前の節と、一覧の項目を突き合わせる。 | テストのない節は、シナリオの追加候補である。新しいシナリオで名前が実装と食い違った場合は、設計を見直す合図である。 |

- 工程2の名前は仮説である。実装がまだないので、工程3のあとに、実装と一致するかを確かめる。これは `naming-as-a-process` の「段階を飛ばさない」の例外である。新しく書くコードでは、呼び出し側の目的が実装より先に決まる。
- 工程3では改名しない。改名はリファクタリングである。食い違いは記録し、工程4で扱う。
- 工程4の改名と責務の分離は、リファクタリングとして扱う。承認がない場合は、候補として記録する。
- `probably_` や `_and_stuff` は、原則として使わない。自分で書いたコードには、未確認の部分が通常ない。既存のコードの理解が不完全な場合は、`naming-as-a-process` の「途中段階の名前の扱い」に従う。
- 一覧を更新するときは、名前から分かったこと（食い違い、分離の候補、欠けている概念）も示す。

## 不具合修正に適用する場合

不具合を再現するテストを、一覧の最初の1件にする。修正の前に、そのテストが不具合のために失敗することを確認する。

## 適用と検証

- アサーションのないテストを、カバレッジを上げる目的で書かない。
- アサーションを削除したり、実際の計算結果をそのまま期待値に貼り付けたりして、成功を装わない。期待値は、実装とは別に求める。
- テストが失敗した原因を確認する。環境やテスト準備の問題による失敗は、対象の振る舞いが未実装であることの証拠にしない。
- 実装中は、選択したテストと関係する既存テストを実行する。完了時には、プロジェクトで必要な検証を行う。実行できない場合は、理由と未確認の範囲を伝える。
- 完了時には、一覧の最終状態と、記録したリファクタリングの候補を報告する。候補には、名前から分かった食い違い、分離の候補、欠けている概念を含める。
- TDD 手順のレビューでは、どの工程に問題があるかを、具体的なコードやテスト結果で示す。
